# Generation service

Сервис принимает заказ на генерацию, списывает токены, отдаёт задачу провайдеру и при отказе идёт к следующей ноге. Если ноги кончились — возвращает токены. Каждое движение денег происходит ровно один раз.

Проверять будут не сценарий «happy path», а гонки, повторные вебхуки и падение воркера. Поэтому инварианты держатся в Postgres, а не в памяти процесса.

## Как запустить

Нужны Docker и Python 3.11+.

```bash
docker compose up --build
```

Поднимаются PostgreSQL, сервис на `http://localhost:8000` в 4 воркерах и два фейковых провайдера: `alpha` (`:8001`) и `beta` (`:8002`).

Миграции применяются при старте контейнера `app` (`alembic upgrade head`).

```bash
# тесты, в том числе обязательные гонки
pytest -q
```

Интеграционные тесты ходят в уже запущенный compose. Юнит-тесты правил маршрутизации работают без Docker.

Локально без Docker:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env
# поднять только postgres из compose, затем:
alembic upgrade head
uvicorn generation.main:app --reload --app-dir src
```

## Миграции

Схема живёт в Alembic, стартовый каталог моделей кладётся первой миграцией.

```bash
# применить все
alembic upgrade head

# добавить следующую
alembic revision -m "add_something"
# правите alembic/versions/..., затем снова upgrade head
```

В Docker то же самое: `docker compose exec app alembic upgrade head`.

Каталог из задания:

| Модель        | Цена | Ноги                                      |
|---------------|------|-------------------------------------------|
| `image-fast`  | 2    | alpha ≤4 референса → beta ≤10             |
| `video-long`  | 25   | beta ≤2 → alpha ≤1, `skip_on_moderation`  |

## API

- `POST /generate` — `{user_id, model_slug, prompt, ref_images}` → `{task_id}`. 402 / 429 / 400.
- `POST /webhooks/providers/{name}` — результат провайдера, HMAC в `X-Signature`.
- `POST /webhooks/payments` — `{payment_id, user_id, tokens, status}`, та же подпись.
- `GET /tasks/{id}` — статус, текущая нога, история попыток.
- `GET /users/{id}/balance` — `sum(ledger.amount)` и последние строки журнала.

Пользователь создаётся первой операцией. Регистрации нет.

Фейковые провайдеры принимают `POST /tasks` и отвечают `202 {"external_id"}`. Их поведение для тестов задаётся `POST /__test__/behavior` (`fail_rate`, `sync_error`, `double_webhook`, `no_webhook`, `late_completed`).

## Почему «ровно один раз»

Журнал — единственный источник баланса. У строки уникальность `(kind, reference_id)`:

- оплата: `kind=payment`, `reference_id=payment_id`
- списание: `kind=debit`, `reference_id=task_id`
- возврат: `kind=refund`, `reference_id=task_id`

Вставка идёт через `INSERT ... ON CONFLICT DO NOTHING`. Двадцать одинаковых оплат или десять `failed` на последней ноге дают одну строку, сколько бы воркеров ни приняли вебхук.

Попытка провайдера закрывается сравнением и обменом: `UPDATE task_attempts SET status=... WHERE id=? AND status='sent'`. Победитель один. Дубль вебхука, одновременный вебхук и сторож, который опоздал на ту же попытку, проигрывают CAS и ничего не двигают в журнале.

Сторож в каждом из 4 процессов выбирает просроченные `sent` через `FOR UPDATE SKIP LOCKED`. Работу не задваивает: одну строку забирает один воркер.

Состояние в памяти процесса не используется. После рестарта живы только строки в Postgres.

## Падение процесса посреди вебхука

Обработка одного события — одна транзакция: CAS попытки, запись в журнал, смена статуса задачи, при необходимости создание следующей попытки.

- Упал до `COMMIT` — в базе ничего не изменилось. Повтор того же вебхука проходит заново.
- Упал после `COMMIT`, до вызова следующей ноги — попытка уже `sent` с `timeout_at`. Сторож либо повторный вебхук продолжат маршрут.
- Упал после вставки возврата — уникальность `(refund, task_id)` не даст второй строки.

Отсюда баланс всегда равен сумме журнала: нет движения без строки и нет двух строк на одно движение.

## Правило 6: поздний `completed`

Если сторож уже закрыл попытку (и, на последней ноге, вернул токены), поздний `completed` игнорируется. Задача остаётся `failed`, `result_url` не ставится, второй возврат не пишется.

Почему так, а не «принять файл и отменить возврат»:

1. Иначе пользователь получает и результат, и токены — ровно то, что запрещено заданием.
2. Сторно возврата само становится вторым денежным событием и снова упирается в гонки.
3. CAS по попытке уже отвечает на вопрос «кто успел первым». Поздний успех провайдера не переигрывает проигрыш по таймауту.

Цена решения: редкий успешно сгенерированный файл после таймаута отбрасывается. Для тестового контура это правильнее, чем дыра в деньгах. Если позже понадобится отдать файл без повторного списания — это отдельный продуктный сценарий, его нельзя смешивать с возвратом.

## Архитектура

```
src/generation/
  domain/          правила ног и ошибки, без IO
  application/     журнал, workflow, сторож
  infrastructure/  Postgres, HMAC, HTTP-клиент провайдеров
  api/             FastAPI
src/providers/     alpha и beta, один код, разный PROVIDER_NAME
```

Стек: Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, PostgreSQL 16. Код проходит `ruff` (PEP 8 + импорты).

## Что не входит

Регистрация, UI, настоящее хранилище файлов, настоящие деньги. Результат генерации — строка-ссылка.
